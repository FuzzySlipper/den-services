# Review service contract

The Review service owns review rounds, findings, verdicts, review packet
validation, and finalization receipts. It is a current-state review authority:
reviewers inspect the repository available when the review is handled and use
the persisted task/round handles and timestamps to reconstruct the context.

The service does not own task lifecycle, message storage, worker assignment,
worker launch, delivery, or legacy dispatch state.

## Authority boundaries

- `projects` validates project ownership and writability.
- `tasks` validates task state, parent/child membership, and conditional task
  transitions.
- `messages` stores task-thread request, findings, response, approval, and
  completion packets.
- Review owns the review state machine and its schema.
- Worker/runtime services own assignment, run, wake, and retry state.
- GitHub check gates are a separate deterministic operation. A gate may track a
  supplied commit identity when CI evidence is explicitly required, but review
  rounds and packets do not carry that identity.

## Active schema boundary

The owning schema is `den_review`. The active round projection contains:

```sql
create table den_review.review_rounds (
    id bigint generated by default as identity primary key,
    project_id text not null,
    task_id bigint not null,
    round_number integer not null,
    requested_by text not null,
    target_kind text not null default 'code_diff',
    campaign_children jsonb not null default '[]'::jsonb,
    campaign_repositories jsonb not null default '[]'::jsonb,
    branch text,
    base_branch text,
    tests_run jsonb,
    notes text,
    verdict text,
    verdict_by text,
    verdict_notes text,
    requested_at timestamptz not null default now(),
    verdict_at timestamptz,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    unique(project_id, task_id, round_number)
);
```

The repository still has historical database columns from an earlier review
contract. They remain for non-destructive compatibility with existing data,
but active Review reads do not project them and active writes do not populate
them. Removing those columns is a separate database-retirement decision.

Findings remain structured rows owned by Review:

```sql
create table den_review.review_findings (
    id bigint generated by default as identity primary key,
    project_id text not null,
    finding_key text not null unique,
    task_id bigint not null,
    review_round_id bigint not null references den_review.review_rounds(id) on delete cascade,
    finding_number integer not null,
    created_by text not null,
    category text not null,
    summary text not null,
    notes text,
    file_references jsonb,
    test_commands jsonb,
    status text not null default 'open',
    status_updated_by text,
    status_notes text,
    status_updated_at timestamptz,
    response_by text,
    response_notes text,
    response_at timestamptz,
    follow_up_task_id bigint,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now()
);
```

## Round creation and current-state review

`create_review_round` and `request_review` accept:

- `requested_by`;
- optional `branch` and `base_branch` labels;
- optional `tests_run` and `notes`;
- optional thread/run correlation fields.

They do not require or accept source-control revision fields. A request creates
the next round, or an identical undecided request reuses the existing round
and packet. Identity is based on project/task, target kind, actor, branch
labels, tests, notes, and the current request context—not on a submitted
source revision.

`request_review` also appends the review request packet and asks Tasks to move
an eligible task from `in_progress` to `review`. A competing terminal task
state returns a typed error without claiming a successful transition.

`list_review_rounds`, workflow summaries, and reviewer context expose the
current round and its evidence handles. They do not manufacture a revision
from the repository or require a reviewer to compare one.

## Campaign reconciliation

Campaigns use named repositories and approved child round pointers:

```json
{
  "requested_by": "campaign-agent",
  "children": [
    {"project_id": "den-services", "task_id": 6097, "review_round_id": 70}
  ],
  "repositories": [{"repository": "FuzzySlipper/den-services"}],
  "tests_run": ["go test ./..."]
}
```

The service validates repository names, duplicate child/repository entries,
campaign membership, latest child rounds, approved child verdicts, and
unresolved blocking or acceptance findings. It stores an immutable typed
snapshot of the names and child membership. No repository entry is matched to
a child source revision. The detailed campaign contract is
[`campaign-reconciliation-reviews.md`](campaign-reconciliation-reviews.md).

## Findings and verdicts

Finding categories are `blocking_bug`, `acceptance_gap`, `test_weakness`, and
`follow_up_candidate`. Finding statuses are `open`, `claimed_fixed`,
`verified_fixed`, `not_fixed`, `superseded`, and `split_to_follow_up`.

`looks_good` requires no unresolved findings for the current task.
`changes_requested` requires an actionable finding in the current round.
`follow_up_needed` and `blocked_by_dependency` are exceptional operator
verdicts and remain available through the controlled compatibility path.

Finding responses preserve response notes separately from status notes. A
follow-up split creates or reuses the Tasks-owned follow-up task and never
silently splits a blocking finding without the explicit override.

## Markdown packets

Packets use `den_review_packet` front matter with `schema_version: 1`, typed
project/task/sender/round identity, packet kind, and a required `verify` list.
The typed envelope is authoritative; prose is evidence for humans and agents.

Review request packets contain current branch context, tests, notes, campaign
child/repository names when applicable, and handles to the owning records.
Findings, response, and completion packets contain finding keys/statuses,
responses, verdicts, tests, notes, and evidence handles. None requires a source
revision field or a copied diff.

Validation rejects missing task/round identity, unknown packet kinds, missing
required verification items, wrong task/round membership, malformed finding
references, or a verdict inconsistent with current findings. A stale round is
identified by the current round number/ID and task state.

`post_review_packet_markdown` and `validate_review_packet_markdown` are bounded
read/write paths. They must not infer lifecycle authority from arbitrary
metadata or from an untrusted source-control claim.

## Finalization

`finalize_review` is the durable green path. It:

1. locks the task/round boundary;
2. proves that the requested round is still current;
3. validates finding resolutions and the verdict;
4. stores one idempotent finalization and canonical packet;
5. appends the task-thread message through Messages;
6. applies the Tasks-owned conditional transition; and
7. returns a compact `den_review.completion_receipt.v1` with IDs, statuses,
   timestamps, and evidence handles.

Retries with the same normalized decision identity return the existing receipt.
A different decision for a committed round returns a typed conflict. Packet
delivery or task transition failures remain retryable and are reconciled
against the same finalization rather than creating a new round.

## Workflow context

`get_review_context` is a bounded composed read. It returns the current task,
repository/root handle, current round, campaign snapshot, concise findings,
packet headers, guidance handles, source status, truncation metadata, and
detail references. When no current round exists it returns a typed
`review_context_unavailable` result with `no_current_round` rather than a
generic task briefing.

An explicit GitHub gate can appear as separate gate evidence in the context
when one was registered through the gate API. If no gate exists, the context
is ready for source review; it does not invent a gate requirement.

## Service routes

The active REST surface includes:

- `POST /v1/projects/{project_id}/tasks/{task_id}/review/rounds`;
- `POST /v1/projects/{project_id}/tasks/{task_id}/review/request`;
- `POST /v1/projects/{project_id}/tasks/{task_id}/review/campaign-request`;
- round, finding, packet, workflow-summary, and finalization routes under
  `/v1`;
- explicit GitHub check discovery, gate registration, read, and wait routes.

MCP exposes the same boundaries through the current review tools. Tool
descriptions should tell agents to review the current checkout and should not
ask them to fill out revision paperwork.

## Migration and verification

The Review service is registered in `deployment/services.yaml` only when its
real contract is available. Cutover uses the service deployment and route
readback procedures; it is not part of packet creation.

Focused tests cover round idempotency, current-round staleness, finding
transitions, packet validation, campaign membership, finalization recovery,
Postgres projections, bounded workflow context, and pointer fixtures. GitHub
gate tests separately cover deterministic check-run matching. Playtests are
black-box current-checkout evidence and do not participate in review-round
matching.

## Non-goals

- copying legacy review tables into a new service without an authority plan;
- storing source snapshots or requiring reviewers to recreate a prior checkout;
- making Review a task, message, worker, deployment, or GitHub Actions owner;
- using packet prose or optional metadata as a hidden lifecycle trigger;
- replacing deterministic deployment/gate checks with agent judgment.
